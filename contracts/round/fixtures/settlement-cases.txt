#
# Read by:
#   contracts/round/src/test.rs              (include_str!)
#   services/keeper/src/settlement-guard.test.ts
#
# Both suites assert the same rows, so the round contract's rules and the
# keeper settlement guard's rules cannot drift apart. Editing one side only
# fails the other suite.
#
# Syntax: fields are separated by '|', lists are separated by ','.
# Blank lines and lines starting with '#' are ignored.
# Fields:
#   name        stable case id, referenced by both suites
#   action      settle | void        the submission the keeper is asking for
#   rule        HighestBid | LowestBid
#   status      on-chain status when the guard is asked to act
#   grace       1 = now is past reveal_deadline + VOID_GRACE, 0 = still inside
#   bids        bid value per bidder (index aligned with escrows/revealed)
#   escrows     locked escrow per bidder; ?(N) = the keeper could not read
#               that bid state (N is the escrow the contract actually holds)
#   revealed    1 = the bidder revealed before clear, 0 = it never did
#   read        how many bidders of the index the keeper actually read
#               (< #bids means the bidder page was truncated)
#   winner_idx  index of the winner after clear, -1 = nobody won
#   operator    operator payout when the contract accepts the action
#   surplus     winner's escrow surplus when the contract accepts the action
#   refunds     escrow the contract returns for this action, as idx:amount;
#               '-' when the contract rejects the action (nothing is paid)
#   guard_reason  '-' = the guard may submit, otherwise the typed refusal the
#               guard must return for this exact view
#   contract    ok = the contract accepts the action, otherwise the error name
#               it must reject with
#
# Agreement rule asserted by both suites: every row the contract rejects has a
# guard_reason, i.e. the guard never submits what the contract would revert.
#
# The rows this fixture exists for — the guard and the contract disagreed on
# all three before Issue #385, because the guard happily submitted them:
#   no-valid-bids-voided     settle → contract answers RoundVoided
#   void-of-revealed-round   void   → contract answers NotVoidable
#   void-inside-grace        void   → contract answers NotVoidable
# Both suites now assert the guard refuses each of them before submitting.

# `truncated-bidder-page` are rounds the contract accepts, which the guard
# still refuses because its local view cannot prove the refund set.
